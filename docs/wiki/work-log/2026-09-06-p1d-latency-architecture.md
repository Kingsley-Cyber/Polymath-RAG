# WORK LOG — P1.d latency architecture

Plan gate (ledger row, read from disk before this phase): *on B: exactly 1 embedding per distinct query text and exactly 1 rerank call per turn (spy tests); HYBRID p50 ≤ VECTOR p50 + 0.5 s; a lane forced past its deadline yields a `degraded` receipt and a complete answer in ≤ core budget + rerank budget.* Goal additions: interactive work must have priority over latent-enrichment traffic on the device; measure p50/p90 per stage and OOM on a controlled machine state; HYBRID must not be effectively serial.

## Contract

- **CONCURRENCY-DEADLINES-V1 (engine).** `retrieve_candidates` submits every independent lane at T=0 in a fixed order (global dense child, global sparse child, document summaries, section summaries, entity cards, each subquery's B and C) to a bounded pool (`executor=` from the route, else a per-call pool of `max_workers` = 8, shut down `wait=False, cancel_futures=True` on every path). One absolute deadline is set at entry (`lane_deadline_s`, 3.0 s): it gathers the four routing lanes, aggregates documents, fans the hierarchical deepening out as one task per selected section, then joins lane C and the subquery lanes; the second pass runs the same way. Results are collected by lane name and fused in the fixed lane order, so the union never depends on completion order: with no deadline hit the output is byte-identical to the sequential engine and the per-lane failure semantics are unchanged (core dense lanes raise, sparse degrades as `sparse_lane`, entity cards stay silent). A lane still pending at the deadline is dropped (late result ignored; a stage whose budget is already spent is not launched, which keeps the receipt deterministic) and recorded as `{"component": "<lane>_timeout"}` in `degraded` and `trace.concurrency.timed_out`.
- **Route.** One pool per turn; lane C for the primary and each subquery is submitted BEFORE the single `_embed_queries` call and handed in via `prestarted=` (BM25 needs only the compiled text, §3.16 stage 2); exactly one `_rerank_children` call per turn, run under `rerank_deadline_s` (3.0 s; expiry → fusion order + `rerank_timeout` in `meta.degraded`, the worker-thread `RerankUnavailable` note carried back so `degradations()` still reports a parked sidecar); an over-budget embedding is receipted as `embed_deadline` (`embed_deadline_s` 2.5 s) while still awaited (hard dependency, never dropped). `lanes=` restricts the composition (VECTOR = HIERARCHICAL_ROUTE + GLOBAL_DENSE_CHILD, HYBRID = + GLOBAL_SPARSE_CHILD; unknown lane → 422 `unknown_lane`); `meta.lanes`, `meta.deadlines`, per-stage `latency_ms` (`embed`, `sparse_prestart`, `lanes`, `lane_<name>`, `union`, `rerank`, `compose`, `rerank_select`, `total`). Env knobs `POLYMATH_CHAT_{EMBED_DEADLINE_S,LANE_DEADLINE_S,RERANK_DEADLINE_S,MAX_WORKERS}` through `default_budget()`.
- **METAL-LEASE-V1 (device).** `polymath_shared.metal.device_lease(priority)` is an `fcntl.flock` lease over three files under `$POLYMATH_FLEET_DIR` (`metal_lease.device` = the mutex held per device batch, `metal_lease.interactive` = held SHARED by every registered interactive caller, `metal_lease.gate` = serialises background probes). Interactive callers register on the marker and take the device as soon as the running batch releases; background callers acquire only when no interactive caller is registered (`yielded=True`, 20 ms back-off) and never hold anything while sleeping. Budgets: interactive 10 s, background 30 s (`POLYMATH_METAL_LEASE_{INTERACTIVE,BACKGROUND}_TIMEOUT_S`); on expiry the caller proceeds unleased (`timed_out=True`, warned once per class). Fail-open: unwritable lock dir or `POLYMATH_METAL_LEASE=0` degrades to a process-local lock; `run_adaptive` / `release` / `is_oom` unchanged. Both sidecars read `X-Polymath-Priority` (default background), lease every device batch (OOM-halving retries stay inside the lease), keep an interactive request registered between its batches (`priority_scope`), and return `queued_ms` + `priority`; readiness probes take a 5 s background lease. Clients: `EmbedderClient(priority=)` / `RerankerClient(priority=)` send the header; `apply_rerank(..., priority=)`; the chat path (`_embed_queries`, `_rerank_children`) is interactive, every other caller background. `POLYMATH_SIDECAR_THREADED=1` (default off) runs device work in the threadpool so a request arriving mid-batch can register its priority inside the process too.
- **Untouched (§3.23):** enrichment workers, their batch sizes, control/. The lease arbitrates the device; it does not change what enrichment computes.

## Proof

**Measurement plan (executed in this order, each on frozen plans through `scripts/chat_m_replay.py`):**
1. Concurrency only (engine commit, lease not yet deployed): B replay → per-stage p50 vs the P1.c final run (`chat-m-replay-p1c-final2-B`), `lanes_wall` vs the sum of lane timings, spy tests for one embedding / one judge.
2. Lease deployed (sidecars respawned with the code): B replay → OOM events per turn, embed p50, rerank p50, `queued_ms`; then the M multi arm for P1.b's absolute latency under priority.
3. HYBRID vs VECTOR: B replay with `--lanes AB` and `--lanes ABC` interleaved per question → p50 delta (gate ≤ 0.5 s).
4. Forced deadlines: 10 B questions with `POLYMATH_CHAT_LANE_DEADLINE_S=0.05` (lanes time out → `<lane>_timeout` receipts, complete answer) and 10 with `POLYMATH_CHAT_RERANK_DEADLINE_S=0.3` (→ `rerank_timeout`, fusion order); wall ≤ core + rerank budget.

**Arm 1 — concurrency only (engine + route integrated, sidecars still on the pre-lease code; `chat-m-replay-p1d-B-conc` vs `chat-m-replay-p1c-final2-B`).** Lanes: 373 ms wall for all primary lanes in parallel (document summaries 77, sections 84, entity cards 69, global dense 68, hierarchical deepening 249 — previously sequential, 550–1 450 ms), BM25 prestarted in 30 ms before the embedding; union 0.3 ms, compose 0.1 ms. Wall p50 14.0 → 8.75 s (clean turns 10.61 → 8.03 s), total retrieval p50 13.95 → 8.67 s; OOM during the run: embedder 0, reranker 8. **Benchmark finding that changed a default:** with the §3.16 starting value `rerank_deadline_s` = 3.0 s the judge timed out on **30 / 30 turns** (24 pairs at ~240 ms/pair is 5.8 s on a fresh sidecar) and composition silently ran on fusion order — survival stayed 0.852 but MRR moved 0.578 → 0.562 and hit@10 0.667 → 0.767 by luck of the fusion order, i.e. the deadline had disabled the judge. The default is now **8.0 s** (fresh case + margin; still catches the 27–52 s thrash case), recorded on the field; `embed_deadline_s` 2.5 s fired on 25 / 30 turns as a receipt (embed p50 4.6 s under contention, never dropped).

**Arm 2/3 diagnosis (before the corrective attempt).** (1) The HYBRID − VECTOR delta is not lane C: per question the median Δembed is 0.0 s and lane C prestarts in 25 ms; the median Δrerank is +0.8 s and HYBRID hit the 8 s judge deadline on 10 turns against VECTOR's 2 — and HYBRID always ran second in each interleaved pair (order bias: the second judge call of a question lands on a device the first one just fragmented). (2) The lease arm's embed waits (18 / 30 turns > 5 s, 10 > 10 s, max 107 s) are the embedder's single-threaded FIFO: both sidecars are `async def` handlers calling the model synchronously, so an interactive request that arrives while a background request is being served cannot even register until that whole request (all its batches and OOM-halving retries) is done — the cross-process lease cannot reorder what one event loop serialises; on top of that `leased_run_adaptive` held the device across the OOM-halving retries of a background batch. (3) 13 / 30 judge calls exceeded 8 s under this load and fell back to fusion order — that is why the M arm's system-honest reading dropped to 0.917 (five dimensions on rerank-timeout turns: no judge score, nothing to show or flag) and B survival read 0.815 instead of 0.852.

**Corrective attempt (one, targeted):** lease per attempt (the device is released between OOM-halving sub-batches), `POLYMATH_SIDECAR_THREADED=1` for both sidecars (device work in the threadpool, so a request arriving mid-batch registers its priority and the lease orders the batches), alternating arm order per question in the harness; sidecars respawned by the supervisor; arms 2 (B) and 3 (AB vs ABC) re-run. **Attempt 2 results (`chat-m-replay-p1d2-B-lease`, `-B-modes`, `-M-lease`).** B under the lease: wall p50 11.75 → **8.39 s** (clean 6.02 → 6.72 s, 22 clean turns), embed p50 5783.8 → **1645.8 ms** (turns > 5 s: 18 → 6, max 25.1 s), rerank p50 4823.8 → 5078.1 ms, judge timeouts 13 → **9** / 30, total p90 49839.3 → 17957.3 ms, OOM events embedder 31 → **0**, reranker 9 → 8; quality survival 0.815, hit@10 0.633, MRR 0.591, avoidable dominance 0. HYBRID vs VECTOR with alternating order: VECTOR 6.14 s (clean 6.05), HYBRID 9.55 s (clean 6.56) → **delta +3.41 s** (clean +0.51 s; attempt 1 +1.41 s) against ≤ +0.5 s; judge timeouts VECTOR 1 / HYBRID 10. M multi under the lease: wall p50 12.13 → 10.03 s (clean 7.29), strict 0.917, system-honest 0.917 → **0.933**, judge timeouts 14 / 30, OOM 0 / 9.

**Arm 2 — lease deployed (both sidecars respawned by the supervisor with METAL-LEASE-V1; `chat-m-replay-p1d-B-lease`, `-M-lease`).** B: wall p50 11.75 s (clean 6.02 s, 17 clean turns), embed p50 5783.8 ms (arm 1: 4571.5; P1.c final: 2940.1), rerank p50 4823.8 ms (arm 1: 3005.2), total p50 11708.7 ms, total p90 49839.3 ms; OOM events during the turns: embedder 31 / reranker 9 (arm 1: 0 / 8; P1.c final: 7 / 11); degraded turns 21 ['embed_deadline', 'rerank_timeout']; quality unchanged: survival 0.815, hit@10 0.667, MRR 0.581, avoidable dominance 0. M (multi, the P1.b absolute-latency question): wall p50 12.13 s (clean 10.28 s) against R1's 10.76 s (clean 10.37 s) and the P1.c final 11.37 s; embed p50 4406.7 ms, rerank p50 7634.8 ms; strict 0.9, system-honest 0.917; OOM 0 / 10.

**Arm 3 — HYBRID vs VECTOR, interleaved per question (`chat-m-replay-p1d-B-modes`, arms `AB` and `ABC`).** VECTOR (A+B) wall p50 8.69 s (clean 8.1 s), HYBRID (A+B+C) 10.1 s (clean 10.09 s): **delta +1.41 s** (clean +1.99 s) against the gate ≤ +0.5 s; lane C prestart p50 25.2 ms; quality VECTOR survival 0.826 / hit@10 0.633 / MRR 0.474 vs HYBRID 0.815 / 0.667 / 0.564; OOM 0/3 vs 1/6.

**Arm 4 — forced deadlines (10 B questions each).** `POLYMATH_CHAT_LANE_DEADLINE_S=0.05`: degraded turns 10/10 with ['document_summary_timeout', 'embed_deadline', 'entity_card_timeout', 'global_dense_child_timeout', 'hierarchical_children_timeout', 'rerank_timeout', 'section_summary_timeout'], every turn answered (errors 0), wall p50 17.81 s, gold in union 0.7, survival 0.714; `POLYMATH_CHAT_RERANK_DEADLINE_S=0.3`: degraded turns 10/10 with ['embed_deadline', 'rerank_timeout'], wall p50 17.9 s, rerank p50 307.9 ms, hit@10 0.5 (fusion order), errors 0.

**Unit proof:** 78 tests passed in the chat/engine/lease suites (+5 engine, +5 route, +19 lease tests); spies: one `_embed_queries` call per distinct text set and one `_rerank_children` call per turn (`test_chat_retrieval_v2.py`), lanes concurrent / deadline drop / order independent of completion (`test_candidate_engine.py`), lease exclusion + interactive-before-background + fail-open (`test_metal_lease.py`).

## Rejected claims

- "Keep the §3.16 starting rerank budget of 3.0 s." Rejected by benchmark (arm 1): it is below this reranker's physical floor and timed the judge out on 30/30 turns, turning the composer into fusion order without anyone asking for it. §3.16 calls its numbers "starting budgets (to benchmark)"; the benchmarked default is 8.0 s, receipted on the field.
- "Make the per-pair cost the fix (fp16 reranker, larger HTTP batches)." Deferred, not rejected: it is a sidecar model change with calibration consequences; P1.d owns arbitration and budgets, not the model. `RERANK_BATCH_SIZE` 16 → 32 (one HTTP call for a 24-pair turn) is recorded as the next cheap step.
- "Run device work in the sidecars' threadpool by default (`POLYMATH_SIDECAR_THREADED=1`)." Kept opt-in: the lease as deployed arbitrates across processes (the OOM coincidence); in-process FIFO behind enrichment requests inside the embedder is a second-order effect measured here through `embed` p50 and left for the owner to switch on after a measured A/B.
- "Interleave lease ON / OFF per turn." Impossible without restarting the sidecars per turn; the lease arm is compared against the same-code arm 1 run minutes earlier under the same enrichment regime, with OOM counts and `queued_ms` as the mechanism-level evidence.
- "Drop late lanes' threads." Rejected: a lane past its deadline is ignored, not cancelled — the Qdrant client timeout bounds the thread; cancelling mid-request would need an async client rewrite (nothing under §3.23 touched).

## Open contract gaps

1. **Absolute retrieval latency is still above the plan's core + rerank budget (6 s)** whenever enrichment runs: the judge alone needs ~5.8 s for 24 pairs on a fresh sidecar. The lease removes the coincidence penalty; the per-pair cost is the model's. Next lever: `RERANK_BATCH_SIZE` 32 and an fp16 reranker on MPS (owner decision — calibration).
2. **`embed_deadline_s` (2.5 s) is a receipt, not a control.** Under contention it fires on most turns; under the lease it should be rare — the number in Arm 2 says which. Whether to raise the interactive embedder wake budget (#18, `POLYMATH_EMBED_WAKE_BUDGET_S` 150 s today) is unchanged by this phase.
3. **The lease is honoured only by processes that take it.** The two v4 sidecars do; the v33 sidecars on 8081/8082 (if resident) and any future device user must call `device_lease` or they bypass the arbitration silently. `lease_stats()` counts yields and timeouts for the receipts.
4. **Threads of late lanes and a timed-out judge live on until their client timeouts** (Qdrant 60 s, reranker 60 s) — bounded background work visible under load; an async client would be the clean fix.
5. **OOM-halving is not only coincidence.** With device use serialized by the lease (embedder log at 03:54Z: `background probe batch yielded to interactive work; queued 3546 ms`, seven yields in the first minutes), the reranker still logged `rerank batch OOM at 8 pairs` and the embedder `mps oom on 8 embed items` while the other process held no batch — two resident models plus allocator fragmentation exceed the Metal pool on their own for the largest batches. The lease removes the queueing and the double-allocation spikes; the residual OOM retries are a memory-residency matter (per-process MPS memory fraction, `POLYMATH_MPS_CAP_GB` is 0 today, or a smaller enrichment batch — the latter is the owner's §3.23 call). Readiness probes now take a 5 s background lease and can report a busy sidecar as not ready during a long batch (`metal lease: background probe waited 5023 ms … proceeds unleased`).
6. **`meta.mode` still reads HYBRID when `lanes=` restricts to A+B**; `meta.lanes` is truthful. P1.e's recomposition renames the mode.
