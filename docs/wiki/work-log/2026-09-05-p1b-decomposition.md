# WORK LOG — P1.b decomposition + aspect coverage

Plan gate (ledger row, read from disk): *multi-dimension fixture: every dimension ✓ or explicitly flagged weak; no document exceeds one vote per subquery; wall p50 ≤ baseline + 3 s.*

## Contract

- **Subqueries (§3.16).** `SubQuery {query_id, qtype, text, weight, qvec, sparse_query, sparse_rule}`; the primary runs A + B + C, every subquery B + C only (`subquery_dense_k` 20, `subquery_sparse_k` 15, `max_subqueries` 3). Lane A is never invoked for a subquery (unit-tested with a spy).
- **One embedding call.** `fast._embed_queries(texts)`: the primary and every distinct subquery text in ONE embedder request; `latency_ms.embedded_texts` receipts the count.
- **Fusion (§3.10).** `query_scores[qid] = weight × Σ_lanes rrf(rank)`; per (subquery, document) the best chunk keeps the full score and the others half; `fused_score = best + min(best, agreement_bonus × Σ_others)` (agreement_bonus 0.5 ⇒ ≤ 2×). The primary's contribution stays the three-lane RRF from P1.a. Documents receive routing votes only from the primary.
- **Aspect coverage.** `trace.aspects[qid] = {type, query, weight, lanes: {A?,B,C}, degraded, union, second_pass?}` + `aspect_final` and `weak_aspects` from `select_evidence`; `meta.aspects` (with `final`), `meta.weak_aspects`; answer event `retrieval.aspects`, `retrieval.weak_aspects`; phase `retrieve_done` `aspects`, `weak_aspects`; request block `EVIDENCE COVERAGE BY ASPECT:` naming each compiled query's evidence count or "NO EVIDENCE RETRIEVED: say so explicitly for this aspect" (only when the plan has ≥ 2 queries).
- **Aspect seats (added after attempt 1 — see Proof).** Every subquery gets ≥ `aspect_prefix_seats` (3) of its own best-fused candidates into the judged prefix (the prefix may grow by seats × subqueries above `rerank_max`); after the judge, an aspect is WEAK when it has no candidates (`no_candidates`) or its best judged candidate's sigmoid score is below `aspect_weak_floor` (0.5, i.e. logit < 0: `below_floor`); every non-weak aspect not yet represented in the final set gets one seat (its best judged candidate) by displacing the lowest item that is not another aspect's only representative. `final_detail[]` (chunk, document, judge score, arrivals, query ids) is receipted for every seated item. With a degraded judge the floor is not applied (no scores): weak means "nothing retrieved".
- **Decomposition guarantee (correction D, added after attempt 2; strengthened after attempt 3).** The compiler prompt now states that every distinct aspect of a compare / contrast / "X and Y" request gets its own typed query; deterministically, `apply_corrections` rule D (`compare_sides`) guarantees that a two-sided "compare A with/and/versus B" request ends up with one query naming side A only and one naming side B only: when the plan lacks that (a single folded query, or a primary that mixes both sides plus a subquery on one of them — measured on attempt 3), it is rebuilt as PRIMARY (A) + COMPARISON (B), keeping any other subquery that does not mix the sides (≤ 4 queries). A plan that already names each side is untouched.
- **Second pass.** The first subquery whose lanes returned nothing runs B + C again at K × `second_pass_factor` (2); at most one per turn; receipted as `second_pass {query_id, before, after}`.
- **Two readings of the dimension gate.** *Strict* (gold / own-document): ✓ needs the aspect's gold chunk or a chunk of its own document seated for a query naming it. *System-honest* (`dims_system_ok`): the answer shows evidence the judge accepted (sigmoid ≥ 0.5) for a query naming the aspect, or the aspect is flagged, or it is strictly ✓ — this is what "✓ or explicitly flagged" means from the system's own vantage (it cannot know the fixture's gold). Both are reported; five of the residual strict misses are B's known unretrievable heading anchors.
- **Fixture M.** `chat_baseline.py --build-multi`: each B item paired with its corpus neighbour (different document) → "Compare what the book says about X with what it says about Y."; per aspect: ✓ (`covered`) = the final set holds one of the aspect's gold chunks (`covered_gold`) OR a chunk of the aspect's own document seated for a compiled query that names the aspect (`covered_doc`, from `final_detail`); flagged = a compiled query naming the aspect is in `weak_aspects`; OK = ✓ or flagged; `silent` = neither; `unnamed` = no compiled query names the aspect (the compiler did not decompose). Summary: `dims_ok_rate`, `dims_covered_rate`, `dims_covered_gold`, `dims_silent`, `dims_unnamed`, `compiled_queries_mean`.
- **A/B switch.** `retrieval: v2-single` (request) / `--retrieval v2-single` runs the same engine with the compiled subqueries ignored — the before/after pair of this phase is measured on one code state, one sidecar state.
- **Frozen and untouched:** chat-intent-plan-v1 (the compiler's query contract is consumed, not changed), lanes A/B/C budgets for the primary, SYNTHESIS-V2 apart from the coverage lines, CARRY-V2, the funnel, `hybrid-retrieval-v1`, `pass1-retrieval-v2`.

## Rejected claims

- "Let every subquery run the full hierarchy." Rejected (§3.16 #13): document routing is the expensive, document-authoritative path; running it N times multiplies both cost and the document's say. Subqueries add child candidates only.
- "Sum the RRF contributions across subqueries." Rejected (§3.10): with LLM-written subqueries the same chunk appears under near-duplicate formulations; a linear sum makes the planner's redundancy the ranking signal. Best + bounded agreement keeps agreement as evidence without letting it outrank a stronger single hit; the unit test pins the ≤ 2× bound and the one-full-vote-per-document rule.
- "Embed subqueries one by one." Rejected: the embedder round trip is ~2 s under today's contention; one batched call keeps the turn inside the +3 s gate.
- "Flag weak aspects only in the receipt." Rejected: the gate says *explicitly* flagged; the model is told which aspect has no evidence so the answer names it instead of improvising.

## Open contract gaps

0. **Two P1.b gates are recorded as MISSED on the shipped code (owner stopped the run here).** (a) Dimension coverage: strict 0.883 / system-honest 0.983 against 1.0 — residual = B's unretrievable heading anchors named only by the primary, which is never flagged; the honest fix is to let the primary itself be flagged weak when its best judged candidate is below the floor (a one-line change to `select_evidence`, not measured today). (b) Wall p50 +4.65 s against +3 s under the OOM contention of gap 7c; the extra cost is the aspect-seat prefix growth (≈ 7 judged pairs) — recovering it is P1.d's concurrency plus the sidecar budget, or a smaller `aspect_prefix_seats` (2) measured on a calm GPU.
1. **Decomposition happens only when the compiler emits typed subqueries.** On plain single-topic questions it emits one query 87 / 97 times (measured on B-v2 receipts), so subqueries change nothing there by design; the M fixture measures the two-aspect case. A compiler-prompt change to encourage decomposition is a CHAT-INTENT-PLAN-V1 prompt matter, not a retrieval one.
2. **"One vote per document per subquery" is enforced at child-level fusion** (a document's best chunk keeps a subquery's full contribution, the rest half) and structurally at routing (lane A runs once). A stricter reading — one *chunk* per document per subquery — would drop legitimate multi-chunk answers; recorded as the interpretation.
3. **Composition is still pure relevance** over the fusion-ordered prefix; the aspect-coverage slot of §3.17 (3 of 18) is P1.c, which now has `query_ids` on every candidate to fill it.
4. **Subquery lanes run sequentially** after the primary lanes (each 30–60 ms; the embedding is already one batched call); concurrency is P1.d.
5. **/chat (non-stream) carries no compiler plan** and therefore no subqueries until the runtime is unified (P1.f); the seam is the same `chat_retrieve_v2(subqueries=)` argument.
6. **Fixture M is synthetic** (two B aspects joined by "compare"); the owner's real multi-aspect conversations (§5 #3, #10) join the frozen suite in P1.g.
7. **The reranker sidecar degrades over hours, not under load.** During this phase's first M baseline the same 20-pair rerank took 10–75 s per turn (turns of 14 s → 83 s) with NO ingest activity and the GPU otherwise idle; the process had been up 3 h 35 min. Killing it (supervisor respawn, 10 s) restored 10 pairs → 2.30 s, 20 pairs → 4.69 s immediately. The likely mechanism is the `torch.mps.empty_cache()`-after-every-batch pattern fragmenting the MPS allocator over thousands of calls. Until the sidecar is fixed (P1.d owns the reranker budget), the operational rule is: recycle the reranker slot when `rerank_select` in the receipts drifts above ~3× its fresh value. The P1.a wall numbers measured under this drift are therefore pessimistic; the P1.b before/after pair below was measured on a fresh reranker.
7c. **Root cause of the "drift" (found while measuring attempt 3): MPS out-of-memory thrash under shared-GPU load.** `sidecar_reranker.log` shows `rerank batch OOM at 8 pairs; retrying at 4` and `sidecar_embedder.log` shows `mps oom on 8 embed items … splitting to 4 + 4` clustered exactly around the slow turns (22:28–22:38 UTC). The 8-item embed batches are not chat traffic (a chat turn embeds ≤ 5 texts in one call) — they come from the latent-enrichment / summaries workers, which keep embedding in the background even when no stage ticket changes state for minutes. When such a batch coincides with a chat rerank, both processes exceed the Metal pool, fall into the OOM-halving retry path, and a 20-pair rerank stretches from 2–5 s to 50 s. A sidecar restart clears the fragmented pool and "fixes" it until the next coincidence, which is why the effect looked like uptime drift. Consequences: (i) every wall-clock number in P1.a–P1.b is an upper bound under this contention; (ii) the fix is not in the chat path — it is the GPU budget between the enrichment embedder and the interactive reranker (owner / P1.d: an interactive reservation, or smaller enrichment embed batches, or the reranker off the shared device); (iii) §3.23 forbids touching enrichment here, so it is recorded, not changed.
7a. **Measurement rule learned the hard way: never probe a single-request sidecar while a run is in flight.** Both v4 sidecars serve one request at a time (uvicorn, one model); a timing probe issued during a baseline run queues behind the run's own embed/rerank calls and reports queueing as "slowness" (22 s for one embedding was mostly the runner's 20-pair rerank ahead of it). The before/after pairs below were measured with nothing else in flight; the drift finding in 7 stands on the M-baseline turns themselves (48–83 s with nothing concurrent), not on probes.
7b. **The embedder sidecar drifts the same way.** After the reranker recycle the M turns still took 15–60 s: `trace.latency_ms.embed` was 22.2 s for ONE query vector (single calls 9.3 s / 4.6 s), with no ingest ticket touched in 10 minutes and the process 1 d 8 h old; its health endpoint had stopped answering. A supervisor respawn restored sub-second embedding. Both MLX/MPS sidecars therefore need the same recycle rule (or a fix for the long-running-process degradation); P1.d's interactive-embedder policy (#18) is where it lands. The M before/after pair was measured on freshly recycled sidecars.
8. **The second pass is bounded to one aspect per turn**; a plan with two empty aspects reports the second as weak rather than searching again — deliberate (latency budget), receipted as `weak_aspects`.
