# WORK LOG — P1.a CHAT-RETRIEVAL-V2 lanes

Plan gate (ledger row, read from disk): *on B: gold chunk present in the union ≥ 0.9 (baseline measured first); lexical fixture set (acronyms, identifiers, quoted phrases) hit@union = 1.0; per-lane arrival recorded on 100 % of candidates; `/retrieve`, `/ask`, TRAIL unchanged (reverse-dependent tests).*

## Contract

- **Lanes (§3.14).** A: doc summaries K16 → RRF over doc/section/child/entity-card votes → 6 documents → section summaries K24, 2 per document → 3 children per section (`hierarchy_rank` = deepening order); B: global dense children K50 with in-lane region demotion; C: global sparse children K40 via the projected `bm25` vector. Every candidate: `arrivals[]` (one or more of the three), `query_ids[]`, `hierarchy_rank / dense_rank / sparse_rank`, `dense_score / sparse_score`, later `rerank_score`.
- **Lane C query (query-side only, §3.23 keeps the projection).** The routing collection applies an IDF modifier to the query, but the stored sparse values are raw term frequencies without BM25 saturation, so a chunk that repeats common query tokens still outscores one occurrence of a rare identifier. Lane C therefore searches the plan's `exact_terms` ALONE when there are any ("what the user literally said"), else the topical text with function words stripped (`sparse_query_for`; the rule is receipted as `trace.sparse_rule`). Measured on "UPA": bare token → gold rank 1; the compiler's five-word expansion → gold outside the top 200.
- **Fusion.** Union by chunk id; `fused_score = Σ_lanes 1/(k + rank + 1)` (k = 60) over the ranks a chunk holds — a chunk found by several lanes fuses once per lane, never once per duplicate; noisy regions sink (never deleted); `merged_candidate_max` = 120 (the funnel's `union` is the pre-cap list).
- **Judge and selection.** One `rerank_children` call over the fusion-ordered prefix `rerank_max` (default 20 — see Proof for why not the whole union), candidate set asserted unchanged, pure relevance to `synthesis_max` (15), then the depth profile's neighbour expansion (additive, after the judge). Reranker outage → fusion order + `degraded` (existing NEVER-ERROR-ON-A-COLD-MODEL law).
- **Budget authority (§3.21 #4).** `CandidateBudget` only; env knobs `POLYMATH_CHAT_{RERANK_MAX,SYNTHESIS_MAX,GLOBAL_DENSE_K,GLOBAL_SPARSE_K,MERGED_CANDIDATE_MAX}` for measurement; `shape_budget(resolved_request)` = depth profile for completeness questions (sections 8/doc, 4 children, K60 dense, rerank/synthesis 28, neighbours ±1) and demotion off for document-metadata questions (#14).
- **Isolation (§3.21 #11, §5b 15–16).** All Qdrant reads go through `FastSearcher._filter_for`: representation kind, corpus, doc/parent, hidden generations; the new `sparse_search` uses the same builder (unit-tested identical filters).
- **Degradation (§3.21 #2).** Sparse lane unavailable ⇒ `meta.degraded += {component: sparse_lane, reason}` and the turn completes on A + B; no `SELECT … FROM chunks` scan exists on the chat path.
- **Receipts.** `trace.plan = chat-retrieval-v2`, `trace.engine = candidate-retrieval-v1`, `lane_sizes`, `funnel_lanes {hierarchical, global_dense_child, global_sparse_child}`, `funnel_union`, `pre_g3_order` / `post_g3_order` / `g3_scores`, `budget`, `timings_ms`, `latency_ms`; the answer event adds `retrieval.engine`, `retrieval.arrivals {chunk_id: [lanes]}` and `retrieval.lane_sizes`; the `retrieve_done` phase names the plan and any degraded component.
- **Rollback boundary.** `POLYMATH_CHAT_RETRIEVAL=v1` or `retrieval: "v1"` per request → `hybrid-retrieval-v1` byte-for-byte; latent / utility requests route there automatically (the latent-rescue lane is not a v2 lane yet).
- **Frozen and untouched:** chat-intent-plan-v1, SYNTHESIS-V2, CARRY-V2, the funnel contract, `pass1-retrieval-v2`, `hybrid-retrieval-v1`, `/retrieve`, `/ask`, `/retrieve/plan` (TRAIL), FAST / GRAPH / WILDCARD modes (P1.e).

**How the L gate was reached (three measured attempts, each with a different root cause).** Attempt 1 (first L set): v2 29 / 30 — the miss was `COM-1`, whose only tokens under the shared BM25 tokenizer are `com` (ubiquitous in an e-commerce corpus): hyphenated tokens test the projection's tokenizer (§3.23, frozen), so the builder now excludes them. Attempt 2 (rebuilt set): 29 / 30 — the miss was `UPA`: the gold chunk is in the sparse projection and ranks 1 for the bare token, but the compiler's PRIMARY "UPA animation studio history style" buried it outside the top 200 (raw tf values, no BM25 saturation, so repeated common tokens outscore one rare identifier). Attempt-1/2 artifacts are kept in the session scratchpad; the fixture in the repo is the final set.

## Rejected claims

- "Rerank the whole union (≈100 candidates) — the plan's diagram." Measured on the shipped sidecar (Qwen3-Reranker-0.6B on MPS, batch 8): 10 pairs 2.4 s, 30 pairs 7.6 s, 60 pairs 12.5 s, 100 pairs 24.3 s, 120 pairs 29.3 s ≈ 240 ms per pair, linear. Judging 100 candidates per turn would add ~22 s to every answer. §3.8 anticipates exactly this ("reranker calls ≤ 10 documents each until the sidecar cap is raised"), so v2 judges a bounded fusion-ordered prefix (`rerank_max` = 20, env-tunable) and the funnel receipts show what the prefix costs (LOST_AT_UNION_TRUNCATION vs LOST_AT_RERANK). Raising the prefix is a one-knob measured change once the reranker is faster (open gap #1).
- "Keep the Postgres lexical fallback as a safety net for the chat path." Rejected (§3.21 #2): it loads a corpus's children and scores them in Python on the request path — the latency disaster the plan names. On the chat path an unavailable sparse lane is now a counted degradation; the fallback remains only inside `hybrid-retrieval-v1` for the routes that are not migrated.
- "Lane B and lane C can stay rescue lanes with small caps." Rejected: caps of 3 made them decoration (P0.0 measured NEVER_RETRIEVED 8 / LOST_AT_UNION_TRUNCATION 9 of 30 on B). In v2 a global child competes on its own rank; the document no longer has to win first.
- "The FastSearcher's bm25 companion probe already gives lane C for free." Rejected (§3.21 #1): the companion fires once per dense routing lane (doc, section, child, deepening) and appends sparse-only hits to each, so an exact-match chunk voted several times before the real sparse lane ran. v2 builds the searcher without the query — one sparse search per turn, in lane C, with the same filters.
- "A new global child search may bypass the corpus / generation filters." Rejected by construction and test: dense and sparse share `_filter_for`; the unit test asserts identical `must` / `must_not` (including the hidden blue/green generation) for both.

## Open contract gaps

1. **Reranker throughput is the ceiling on the judge.** The sidecar (`sidecars/reranker/server.py`) loads `CrossEncoder` with defaults — fp32 weights on MPS, `POLYMATH_RERANK_BATCH=8`, and `torch.mps.empty_cache()` after EVERY batch (the OOM guard from P0.a, which also throws away the allocator's warm pool each time). ~4 pairs/s means `rerank_max` 20 (≈5 s) is already 2× today's rerank cost; the plan's "union → top ≈30" and P1.c's "gold survives selection on ≥ 0.85 where in union" need a faster sidecar (larger MPS batch now that passages are ≤ 4,000 chars, an int8/ONNX build, the RTX box, or a smaller cross-encoder). This is a sidecar/provider decision for the owner; the engine takes any speed-up as a budget knob.
1b. **The GPU is shared with processes outside v4.** While timing the lanes the same 10-pair rerank took 2.4 s at 12:50 and 20.3 s at 14:08 with the v4 reranker idle in between; ports 8081/8082 still serve the v33 sidecars (jina-reranker-v3 fp16 and a Qwen3 MLX embedder, `in_flight: false` but resident on the same Metal device), and the cinema ingest keeps the v4 embedder (8742) busy. Wall-clock numbers in this log are therefore contention-dependent; v1 and v2 were measured back-to-back under the same conditions. Retiring the v33 sidecars is an operator decision (launchd), not something this run touches.
2. **Single query only.** Lane C searches the compiled retrieval text (PRIMARY + exact terms). Typed subqueries and per-term sparse probes are P1.b, gated on this phase's seams (#1, #2) being merged — they now are.
3. **Composition = pure relevance.** Source diversity, aspect coverage and multi-lane agreement boost are P1.c; v2 carries the provenance they need on every candidate.
4. **Lanes run sequentially** in one request thread; embedding and sparse tokenisation happen once but do not overlap (P1.d).
5. **FAST, GRAPH and WILDCARD** still run their v1 engines; only HYBRID (the default) is on v2 (P1.e).
6. **Latent-rescue lane** is not in v2: a request with `latent: true` (or `/chat` `utility: true`) routes to `hybrid-retrieval-v1`, receipted by plan version.
7. **`hybrid-retrieval-v1`'s sparse lane has been dead in production** (found while timing the lanes): `orchestrator/api/hybrid.py::_sparse_lexical_search` iterates `_corpus_collections([corpus_id])` — a `{corpus_id: collection}` dict — so it queries a Qdrant collection literally named after the corpus (`cinema`), gets 404, and `_lexical_search` silently falls through to the Postgres Python scan on every HYBRID turn (measured: 404 in 0.11 s, then the scan, 0.83 s on cinema). Seam #2 was not a risk, it was the running state. v1 is left byte-for-byte per the plan's versioning rule (its consumers are /retrieve, /ask, TRAIL — their migration is a separate evaluation); the fix is a one-line `collections.values()` when that evaluation runs. v2 uses the real collection through `FastSearcher` (40 hits in 0.03 s).
8. **Fixture L** covers acronyms and identifiers (document frequency 1–2, case-insensitive); quoted multi-word phrases are not in the set yet (builder extension, no engine change).
