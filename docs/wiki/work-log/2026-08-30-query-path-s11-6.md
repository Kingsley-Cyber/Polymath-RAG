# WORK LOG — QUERY-PATH-S11-6-PHASE1 ("retrieval is all over the place / 113 s answers")

## Contract
Summaries route, children prove; retrieval never calls an LLM at query
time; lanes are additive and fail-open. A query must answer in seconds,
child lanes must contain ONLY children, exact names must not depend on
embedding luck, and graph extractions must be first-class FAST citizens
(register 11.6).

## Changes
- `orchestrator/api/retrieve.py` — CHILD-LANE-KIND-FILTER: the legacy
  dense lane searched the collection UNFILTERED; after §11 all kinds
  (cards, procedures, concepts, summaries) competed inside the child
  lane and surfaced as empty-chunk_id junk. Now
  `representation_kind='routing_child'` + corpus-scoped.
- `orchestrator/api/hybrid.py` — SPARSE-BM25 lexical lane: queries the
  named `bm25` vector with the SHARED tokenizer
  (`polymath_shared.sparse_bm25`); the in-memory `lexical_score` scan
  over every corpus child remains the fallback for legacy dense-only
  collections.
- `orchestrator/api/fast.py` — ENTITY-CARD-LANE-V1: sparse+dense probe
  over `routing_entity` cards (top 8, deduped, best-score), returned as
  `entity_card_lane` + advisory STABLE doc-vote re-rank of selected
  documents; fail-open with LOUD logging. Bug found during landing:
  `_corpus_collections` returns a dict — iterating keys fed corpus ids
  as collection names and the per-collection guard swallowed it (zero
  cards, no error); `.values()` fixed it.
- Query latency: the 113 s answers were `POLYMATH_RERANK_WAKE_BUDGET_S`
  = 90 s spent waking a reranker NOBODY WAS RUNNING (the pipeline
  profile parks it by design; the hand-start was lost across restarts).
  Reranker restarted; orchestrator env runs wake budget 5 s — a dead
  reranker now degrades to fusion order in 5 s, never hangs the query.
- Hygiene: 35 stale summary points (superseded variants) deleted from
  the store; leaked `_probe_sparse_v1` collection removed; corpus
  enabled for query scope (upload defaults are `probe/query_enabled=
  false` — retrieval is scoped out BY LAW until enabled; this, not a
  bug, was the "retrieval constantly fails").

## Proof
Same query, before → after, measured over HTTP: FAST answered in
**2.05 s** (was 113 s), `entity_card_lane` populated ("Amazon S3
[Product]" at sparse 7.31 leading), doc-boost applied, `degraded: []`;
legacy child lanes now return chunk-only hits (kind=child_chunk,
chunk_id present on every row); HYBRID lexical served from the bm25
index. Store hygiene verified by scroll counts (1:1 with authority on
every live kind after cleanup).

## Rejected claims
- "Dense retrieval is broken" — REJECTED: it was scoped out
  (query_enabled=false) and then kind-polluted; the vectors were fine.
- "The reranker should be removed from the query path" — REJECTED: it
  reordered nothing only because it was dead; alive it costs ~0.3 s.
  The fix is the 5 s wake budget, not removal.
