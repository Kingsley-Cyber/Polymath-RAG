TITLE: Post-Incident Review: OAuth Token Replay in the Atlas Identity Gateway

On 7 August 2026, the security engineering team at Northstar Digital observed repeated access attempts against the Atlas Identity Gateway, an internal authentication service deployed in the company’s AWS environment. CloudTrail records showed that a valid OAuth 2.0 access token issued to the Meridian Billing API was replayed from two previously unseen IP addresses after the original user session had ended. The token had been issued by Keycloak 26.2 through the OpenID Connect authorization-code flow and contained the expected audience, issuer, and expiration claims. No evidence indicated that Keycloak itself had been compromised.

The investigation found that the Meridian Billing API logged the complete HTTP Authorization header during a temporary debugging session. Those logs were forwarded by Fluent Bit to an Elasticsearch cluster used by the observability team. A contractor account assigned to Daniel Ortiz, a site reliability engineer working through Red Ridge Systems, had read access to the affected index. Investigators could not prove that Ortiz accessed the token, and the incident report does not attribute the replay to him. The exposure existed because bearer tokens remained usable by anyone possessing the token until expiration; the API did not bind the credential to the originating client.

Northstar disabled Authorization-header logging, rotated the affected credentials, invalidated active sessions, and reduced access-token lifetime from sixty minutes to ten minutes. The platform team also proposed mutual TLS for machine-to-machine traffic and Demonstrating Proof of Possession, or DPoP, for clients capable of generating key-bound tokens. DPoP may reduce replay risk because a stolen access token cannot normally be reused without the associated private key, but it does not prevent token theft or protect a compromised client. The architecture review board therefore classified DPoP as a compensating control rather than a complete remediation.

The incident was categorized using STRIDE as primarily a spoofing and information-disclosure scenario. The security team linked the failure to three control weaknesses: sensitive-data logging, excessive observability permissions, and bearer-token replayability. Amazon GuardDuty did not detect the incident because the requests used valid credentials and did not match the organization’s existing anomaly rules. The company intends to add token-fingerprint telemetry to Atlas, but raw access tokens must not be stored for correlation. Future detection logic will instead record a keyed hash derived from selected token metadata and compare usage patterns across sessions.

A follow-up verification exercise is scheduled for September 2026. The red team will attempt token replay against Atlas after the new controls are deployed, while the identity team will verify that normal service-to-service authentication remains functional. The test will be considered unsuccessful if a captured bearer token can authenticate from an unauthorized client after proof-of-possession enforcement is enabled. Results from the exercise will be reviewed by Northstar’s Security Architecture Council before the control is approved for production.
