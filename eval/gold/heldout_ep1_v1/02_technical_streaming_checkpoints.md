# Design Notes: Streaming Processing with Checkpointed State

A streaming processor consumes a continuous feed of records and maintains derived state that must survive restarts. The central design rule is that the derived state is a function of the input records and the processing logic, never a separate source of truth. A checkpoint mechanism writes the derived state to durable storage at intervals, and the input offsets are written in the same transaction as the checkpoint. After a restart, the processor reloads the checkpoint, seeks the input to the recorded offsets, and resumes without losing committed work or processing records twice.

Exactly-once processing is usually implemented as at-least-once delivery plus deterministic output keys. Downstream systems that receive duplicate deliveries recognize the repeated keys and overwrite or ignore them. The processor itself does not need to remember which records it has seen; the output store does that work by construction. This division of responsibility keeps the processing logic simple and makes the delivery semantics testable in isolation.

Windowed aggregation introduces its own failure modes. A window that closes while a worker is writing its results must decide whether the write committed. The safest pattern is to write the aggregate with the window's identity as the key, then close the window only after the write is acknowledged. A late record arriving after the window closes is either discarded with a counter or routed to a separate correction stream, depending on the tolerance for late data. Both behaviors are explicit configuration choices, not emergent properties of the system.

Testing a streaming processor requires a deterministic event log. A test harness replays recorded input sequences against the processing logic and compares the derived state against an expected state after each record. Randomized ordering tests shuffle the same records and require the final state to be identical, which catches hidden dependencies on arrival order. These tests run without a cluster and are the cheapest place to catch ordering bugs.

Operationally, backpressure is the first symptom of a capacity problem. When downstream consumers fall behind, the processor should slow its reads rather than accumulate unbounded queue depth. Observability metrics expose the input lag, the checkpoint age, and the queue depth, and alerting thresholds are set on those numbers rather than on error rates alone. A system that only alerts on crashes discovers its capacity problems after users have already noticed them.
