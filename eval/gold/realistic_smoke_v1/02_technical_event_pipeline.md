# Designing a Restart-Safe Event Processing Pipeline

A restart-safe event pipeline must assume that processes will fail at inconvenient moments. A worker may crash after writing to a database but before acknowledging a message, a network call may time out even though the remote service completed the request, or a machine may reboot while a batch is only partially processed. The design goal is not to prevent every failure. Instead, the system should make repeated work harmless and make incomplete work visible enough to resume without manual reconstruction.

One common approach is to keep workflow authority in a transactional database. A worker claims an event, performs the stage-specific writes, records a receipt, updates the run status, and emits the next outbox event in one transaction. If the transaction commits, the stage is complete. If it rolls back, none of those changes become authoritative. This pattern avoids the ambiguous state created when a worker updates one system and then crashes before updating another. The outbox can later be delivered to downstream workers without making the message broker itself the source of truth.

Idempotent identities are equally important. Documents, chunks, facts, and projection artifacts can be assigned deterministic identifiers derived from normalized content and stable structural inputs. When the same document is submitted again, the pipeline lands on the same identifiers instead of creating duplicates. A replay can therefore become a no-op at the storage layer even if the orchestration layer retries the same work several times. This is especially useful when external services provide at-least-once delivery rather than exactly-once delivery.

Search indexes and graph databases should be treated differently from the workflow database. A vector index can accelerate semantic retrieval, and a graph store can accelerate traversal, but neither needs to be authoritative if both can be rebuilt from durable records. The projection worker should therefore record what it attempted to materialize and the verifier should compare the projected state with the authoritative receipts. If a projection disappears, the system should clear or supersede the corresponding claim and schedule reconstruction rather than pretending the index is still complete.

Concurrency introduces another class of failure. Two workers may attempt to process the same stage, or one worker may stall long enough that a lease expires and another worker takes over. A robust implementation uses bounded leases, deterministic stage contracts, and transactional claim operations so that only one committed result becomes authoritative. The losing worker must be able to discover that its work is stale. This prevents a delayed process from overwriting a newer run state after ownership has already moved elsewhere.

Operationally, the pipeline is only trustworthy if these properties are tested under failure rather than inferred from clean runs. Useful tests include killing a worker between database writes, replaying the same document repeatedly, deleting a projection and rebuilding it, adding a document after the corpus is already populated, and verifying that unrelated records remain unchanged. A system that passes those tests can scale by adding workers and larger batches without changing its correctness model, because the failure semantics were designed into the workflow rather than patched around it.
