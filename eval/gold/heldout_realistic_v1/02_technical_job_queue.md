# Notes on Building a Job Queue with Idempotent Retries

A durable job queue is built around one idea: executing the same job twice must produce the same committed result as executing it once. This property is not achieved by making the worker careful; it is achieved by giving every job a deterministic identity and by writing every side effect through a transactional boundary. When a job is retried after a crash, the storage layer recognizes the repeated identity and refuses to create a second copy of the result.

The queue itself can be implemented on top of a relational database. The jobs table holds the pending work, a lease column records which worker currently owns each job, and an outbox table carries events that must be delivered to downstream consumers. A worker claims a job by writing its lease inside the same transaction that reads the job, which prevents two workers from taking the same item. If a worker dies, its leases expire and another worker can reclaim the abandoned jobs without human intervention.

Retry policy deserves as much design attention as the storage layer. Retrying immediately after a transient failure is sometimes correct, but retrying an operation that modifies remote systems can amplify the original problem. Exponential backoff with a maximum delay is a common compromise. Each retry is recorded with the attempt number and the observed error, so operators can distinguish a persistent failure from a transient one.

Projections of the job history are treated as disposable. A monitoring dashboard that counts completed jobs can be rebuilt from the authoritative tables, and the same is true of any search index that makes job metadata easy to query. The rule is simple: if a derived store can be reconstructed from the database, losing it is an operational inconvenience rather than a data loss. Verification jobs compare the derived stores against the authoritative receipts on a schedule, and any mismatch is repaired by rebuilding the affected store rather than by hand-editing the projection.

Batch processing introduces a final complication. A batch that fails halfway through must leave the completed items committed and the remaining items clearly retriable. The batch job therefore commits one transaction per item, and the batch record tracks which items finished. Restarting the batch discovers the unfinished items from the batch record instead of guessing from the queue. This design keeps the failure semantics of the single-item path intact at any batch size.
