What I would tell Fable now

Add registry growth/maintenance as a separate lifecycle from opportunity research. Opportunity executions may emit RegistryCandidate objects whenever they encounter a novel niche, activity, atomic task, friction, workaround pattern, shared predicate, physical job, product territory, query strategy, source, or seasonal pattern. Those discoveries persist in the existing SQLite Work Graph but must never mutate the active CSV registry inside the discovering run.

Create a Registry Maintenance Control Graph whose responsibilities are candidate collection across runs, normalization, deduplication/alias resolution, novelty and reusability analysis, evidence/falsification, diversification-gap analysis, promotion eligibility, human approval, CSV patch generation, registry compilation, regression validation, and publication of a new immutable RegistrySnapshot. Wrap that graph in a bounded maintenance loop with progress, budgets, stagnation and named terminal states.

For new niches, do not merely add a niche name. Expand supported niches into atomic activity/task/context/body-state/friction/workaround/shared-predicate seed candidates matching the reasoning grain of the existing 1,386-row outdoor seed corpus. Prefer horizontal growth—new domains instantiated using existing friction/predicate/physical-job primitives—over constantly inventing new primitives. New friction families, predicates, query grammars and especially scoring changes require progressively stronger governance.

Do not rename or restructure outdoor_activity_niche_seed.csv now. Treat it as the first implementation of an AtomicActivitySeed schema. registry.py should eventually be capable of compiling multiple same-schema seed packs so future creator, home, pet, beauty, automotive, or other domains can diversify the registry without contaminating the existing outdoor source file.

Registry growth should be demand-driven by real execution wherever possible: repeated UNRESOLVED resolutions, recurring candidate concepts, frequently used physical predicates with low seed coverage, repeated friction/workaround patterns, and poor registry support for frequently investigated domains should generate diversification candidates. Manual diversification requests should use the same graph and validation process.

The active registry is conservative; the candidate pool may be aggressive. Runtime discovers. Maintenance evaluates. Git promotes. registry.py compiles. Future runs consume the new version.
