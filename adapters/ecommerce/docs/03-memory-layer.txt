SQLite is a good fit here, and I would make one architectural distinction explicit:

> **Hermes memory is agent memory. SQLite is opportunity-loop memory.**

They should not compete or synchronize continuously.

The loop sources require memory to survive outside the conversation so an unattended loop can recover progress and decisions; they explicitly distinguish the harness's internal agent cycle from the external loop specification containing goal, verification, stopping rules, and memory.  The prompt-graph source separately requires the graph itself to remain an explicit, inspectable artifact rather than becoming hidden inside runtime state. 

SQLite is my implementation recommendation; the sources do **not** mandate SQLite.

# 1. Lock the four kinds of memory

This is the cleanest way to prevent the system from slowly becoming confused about authority.

| Memory                 | Purpose                                                        | Authority                |
| ---------------------- | -------------------------------------------------------------- | ------------------------ |
| **Hermes memory**      | General agent knowledge, learned preferences, reusable context | Hermes                   |
| **Polymath**           | Long-term evidence/second-brain knowledge                      | Polymath                 |
| **Git registry**       | Niches, activities, lenses, motifs, policies                   | Curated registry         |
| **Opportunity SQLite** | Exact state of an opportunity investigation                    | Opportunity skill/Python |

The critical rule:

```text
Hermes memory can make Hermes smarter.

SQLite must make the workflow resumable.
```

If Hermes's general memory were completely cleared halfway through a run, this command should still know **exactly** what needs to happen:

```bash
controller.py step --run run_123
```

Likewise, Hermes memory must never be able to say:

> "I remember we already validated that hypothesis."

if SQLite says it hasn't passed the required checks.

That's the separation.

---

# 2. SQLite is almost ideal for this

You don't need another dependency.

Python already ships:

```python
import sqlite3
```

No database server.

No Docker container.

No Mongo deployment.

No Redis.

No SQLAlchemy.

For what we're storing—probably thousands or tens of thousands of compact records per investigation rather than terabytes—SQLite is more than enough.

And because the loop source emphasizes persistent state outside the conversation, a tiny transactional database is actually stronger than a mutable `run1.json` file.


# 10. Why actions must be persisted **before** execution

This is a subtle failure condition Fable should absolutely implement correctly.

Suppose:

```text
controller step
    ↓
tells Hermes:
search Reddit for query Q
    ↓
Hermes crashes
```

If the request only existed in terminal output, the system has forgotten it.

Instead:

```text
controller step
    ↓
BEGIN TRANSACTION
    ↓
create action A
status=PENDING
    ↓
commit
    ↓
print action A to Hermes
```

Now if Hermes crashes:

```bash
controller.py step --run run_123
```

returns **the same pending action**.

It does not generate another query.

That's real loop durability.

---

# 11. `submit` must also be idempotent

Imagine Hermes executes Alibaba research and successfully gets results.

Then:

```text
submit
```

times out after SQLite commits.

Hermes assumes the submission failed and retries.

Without idempotency:

```text
product A inserted twice
supplier A counted twice
query budget decremented twice
```

Bad.

Instead:

```text
idempotency_key =
hash(
    run_id
    + graph_node
    + action_type
    + semantic_input_hash
)
```

`actions.idempotency_key` gets a:

```sql
UNIQUE
```

constraint.

The second submission returns:

```text
ALREADY_APPLIED
```

provided its result hash matches.

If the same action ID arrives with a different payload:

```text
IDEMPOTENCY_CONFLICT
```

and stop.

# 17. Use one SQLite database, not one per run

Do:

```text

```

containing every run.

Not:



But previous-run information should initially be **advisory**, not a hard reason to skip new research.

# 19. Configure SQLite for exactly this workload

Every connection should initialize:

```sql
PRAGMA foreign_keys = ON;
PRAGMA journal_mode = WAL;
PRAGMA synchronous = FULL;
PRAGMA busy_timeout = 5000;
```

I would use `FULL`, not `NORMAL`, initially.

Your write rate is tiny.

I'd rather make the unattended workflow slightly more durable than save milliseconds.

`WAL` means reads and writes interfere less.

`busy_timeout` prevents a short-lived overlapping CLI command from immediately throwing "database locked."

# 21. One logical writer per run

SQLite itself serializes writes, but two Hermes processes could still both try to advance one run logically.

For v1, enforce:

> **At most one PENDING action per run.**

Use a partial unique index:

```sql
CREATE UNIQUE INDEX ...
ON actions(run_id)
WHERE status IN ('PENDING', 'RUNNING');
```

Then two controllers cannot independently tell Hermes two different things are "next."

Later, if you deliberately implement parallel research branches, change this to:

```text
one pending action per branch
```

Don't start there.

# 22. Make `step` almost entirely deterministic

This is the core behavior Fable should implement.

Conceptually:

```text
STEP(run)

1. Load run.
2. Verify graph/policy/loop hashes.
3. If terminal → return terminal.
4. If pending action exists → return same action.
5. Recompute relevant satisfaction checks.
6. Evaluate no-progress condition.
7. Evaluate budget condition.
8. Determine current graph node.
9. Evaluate legal outgoing transitions.
10. Choose deterministic transition.
11. If local Python node:
       execute
       persist
       repeat from #5.
12. If external action required:
       persist PENDING action
       return it.
13. If terminal condition reached:
       persist terminal receipt
       return terminal.
```

No semantic LLM decisions in `step`.

---

# 23. `submit` should be equally strict

```text
SUBMIT(run, action, result)

1. Is this action actually pending?
2. Does action belong to this run?
3. Is result schema correct?
4. Does result hash match an already-submitted result?
5. If duplicate exact result:
       return existing receipt.
6. If duplicate conflicting result:
       reject.
7. Run deterministic verifier.
8. Store admitted/rejected Work Graph deltas.
9. Store verification receipts.
10. Update budgets.
11. Append event(s).
12. Increment run revision.
13. Mark action terminal.
14. Commit everything atomically.
```

If anything fails before commit:

```text
nothing changes
```

That's the advantage SQLite gives you over mutable JSON state.

# 26. Treat every research cycle as causally frozen

The closed-loop quality source has one especially transferable design principle: feedback from one cycle is propagated into the **next** cycle rather than retroactively changing the state used to produce the current result, preserving temporal causality. 

Apply that here.

```text
Cycle 3:
Evidence state E3
→ hypotheses
→ research
→ new observations

New observations DO NOT rewrite E3.

They produce:

Cycle 4:
Evidence state E4
```

So don't mutate old checks.

Append:

```text
ResearchSatisfaction cycle=3
ResearchSatisfaction cycle=4
```

This makes debugging much easier.

when fields are missing.

Version it.

---

# 40. No SQL business logic

Another rule for Fable:

**No SQLite triggers implementing workflow semantics.**

Don't hide:

```text
if comment count >= 12
then mark satisfied
```

inside SQL.

The database should enforce:

```text
types
uniqueness
foreign keys
atomicity
```

Python owns:

```text
meaning
policy
state transitions
satisfaction
```

Otherwise your actual control plane becomes impossible to inspect.

---

# 41. `controller.py` must remain the single transition authority

Even `executors.py` cannot independently advance state.

Correct:

```text
controller
    ↓
executor
    ↓
result
    ↓
controller validates
    ↓
memory transaction
```

Incorrect:

```text
executor
    ↓
updates SQLite current_node directly
```

Only `controller.py` calls the transition operation.

`memory.py` performs the persistence transaction but doesn't decide the next state.

---

# 42. A failed executor is not a failed hypothesis

This subtlety needs explicit error classes.

Example:

```text
Reddit search failed
```

does **not** mean:

```text
hypothesis rejected
```

It means:

```text
ACTION_FAILED
```

and possibly:

```text
SOURCE_CAPABILITY_FAILURE
```

The hypothesis remains:

```text
UNPROVEN
```

Likewise:

```text
no Alibaba result
```

could mean:

```text
supplier search query poor
source blocked
product doesn't exist
```

Those aren't interchangeable.

Keep failure classes separate from semantic verdicts.

---

# 43. Absence of evidence should remain `UNPROVEN`

Don't let:

```text
zero Reddit comments found
```

become:

```text
DISPROVEN
```

You already had this invariant in the broader reasoning design.

Use:

```text
SUPPORTED
CONTRADICTED
UNPROVEN
```

Contradiction requires actual counter-evidence.

---

# 44. Separate terminal state from product verdict

Run terminal:

```text
SUCCESS
NO_DEFENSIBLE_BRIDGE
REJECTED
BLOCKED
STALLED
EXHAUSTED
NEEDS_APPROVAL
```

Product verdict:

```text
QUALIFIED
PROVISIONAL
WEAK
REJECTED
```

A run can successfully terminate with:

```text
SUCCESS
```

because it correctly determined:

```text
product hypothesis rejected
```

"Success" means:

> The loop accomplished its verifiable research goal.

Not:

> We found something to sell.

That is an important loop-engineering distinction.

# 46. The most important new tests for Fable

The 16 tests are a good start. I would make sure the eventual suite contains these failure modes:

| Test                                            | Required behavior              |
| ----------------------------------------------- | ------------------------------ |
| Hermes crashes after `step`                     | Same pending action returned   |
| Hermes retries identical `submit`               | No duplicate mutation          |
| Hermes submits different result for same action | Hard conflict                  |
| `control_graph.yaml` changes mid-run            | Block config drift             |
| SQLite locked for 100 ms                        | Wait/retry, don't corrupt      |
| Invalid Work edge                               | Reject                         |
| Hypothesis exceeds inference-hop budget         | Reject/revise                  |
| `first_inference_at` isn't an edge              | Reject                         |
| Same comment found twice                        | Count once                     |
| 100 comments from one thread                    | Independence gate fails        |
| Research adds no meaningful state twice         | `STALLED`                      |
| Query budget exhausted                          | `EXHAUSTED`, never success     |
| Website unavailable                             | `BLOCKED` or escalate          |
| No research result                              | `UNPROVEN`, not disproven      |
| Strong counter-evidence                         | Hypothesis contradicted        |
| Alibaba listing lacks MOQ                       | Supplier satisfaction fails    |
| Same physical product from five suppliers       | One candidate, five offers     |
| Human promotion required                        | `NEEDS_APPROVAL`               |
| Hermes memory erased mid-run                    | Run resumes correctly          |
| Process killed during SQLite transaction        | No partial state               |
| Old terminal run `step` called                  | Same immutable terminal result |

Those are the tests that make "I walked away" credible.

```text
doctor
```

because this will save significant debugging.

```bash
controller.py doctor
```

checks:

```text
schema version supported

control graph valid
```

# 48. One thing I would *not* add yet: autonomous cross-run learning

SQLite makes this tempting:

> Let the system automatically change its own policies based on prior runs.

Don't.

Initially, use past runs for:

```text
analytics
candidate discovery
query hints
registry candidate proposals
```

but not:

```text
automatic threshold modification
automatic traversal-rule modification
automatic prompt replacement
```

That's where unattended loops can become self-corrupting.

The loop literature emphasizes that autonomy increases the importance of sharp evaluators and retained human checkpoints, not the opposite.

# 49. Later, you can add Experience Memory without changing this architecture

Once you have enough runs, SQLite can surface things like:

```text
Query template X:

consistently useless

Lens Mobility:
frequently useful for creator tools

Reasoning motif:
hands occupied → hands-free
validated across 7 independent domains

Alibaba query formulation:

```

Those become **candidates for reusable skill/registry knowledge**.

But they promote outward:

```text
SQLite history
    ↓
candidate
    ↓
review/evaluation
    ↓
Git registry / skill update
```

They don't silently alter the current loop.

That is how the system compounds without drifting.

# What I would hand Fable as the persistence lock

> **Add SQLite as local workflow memory, not agent memory and not knowledge memory. Place the database outside the skill installation directory. `memory.py` is the sole SQLite adapter. `controller.py` remains the sole transition authority. The Control Graph, Loop Specification, policies, schemas and registry remain Git/YAML/CSV artifacts and are hash-pinned into each run. SQLite stores runs, temporary Work Graph nodes and edges, external actions, append-only events, and verification/satisfaction receipts. Persist every external action before giving it to Hermes; make submission idempotent; make transition writes atomic; never infer semantic truth from infrastructure failure; never treat lack of evidence as contradiction; never resume against changed graph/policy hashes; never store large source documents/images/browser telemetry; and make every terminal state, research decision and product lead reconstructable without Hermes conversational memory.**

And the final memory architecture becomes:

```text
                    HERMES MEMORY
                general agent knowledge
                         │
                         │ contextual help
                         ▼
                    HERMES AGENT
                         │
       ┌─────────────────┼────────────────┐
       │                 │                │
       ▼                 ▼                ▼
   POLYMATH          SQLITE           GIT REGISTRY
 long-term facts    current work     reusable priors
 evidence memory    loop memory      reasoning memory
       │                 │                │
       └─────────────────┼────────────────┘
                         ▼
                 OPPORTUNITY SKILL
                         │
                         ▼
                    CONTROL GRAPH
                         │
                         ▼
                      LOOPS
```

**SQLite is therefore not a fifth intelligence system. It is just the small durable notebook φ needs so Hermes can forget the conversation, crash, restart, or run unattended without forgetting where the investigation actually stands.**
