Yes. The missing piece is not another settings file; it is a **Hermes Preference Control Plane** that lets Hermes inspect the skill and determine, from the code/graphs themselves, **what the user is allowed to tune**.

Fable should not manually hard-code a menu like “products/comments/hops.” It already knows the codebase. Have it make the skill **self-describing** so Hermes can discover adjustable controls automatically.

## The core design

The flow should be:

```text
USER
"I want it to keep digging until it finds
at least 12 decent product candidates,
go heavy on comments,
and give me 5 final products."

        ↓

HERMES
interprets preference intent

        ↓

SETTINGS REGISTRY
"What controls does this mode actually expose?"

        ↓

settings.py
validates + resolves preferences

        ↓

ResolvedRunPreferences
frozen in SQLite

        ↓

CONTROL GRAPH + LOOP
consume those preferences

        ↓

RUN
```

Hermes should therefore be able to answer:

> “What can I change for this research mode?”

by **reading the mode's setting definitions**, not from prompt memory.

# Loop controls should work the same way

This is especially important for what you're describing.

A user might say:

> “Keep looping until you find enough.”

That should **not** translate into an unbounded loop.

It should compile into a satisfaction target plus hard safety ceiling.

For example:

```yaml
user_goal:
  discovery:
    min_product_candidates: 12

  evidence:
    community_strength: STRONG

  final:
    final_products: 5

loop_preferences:
  continue_while:
    - product_candidates < 12
    - critical_evidence_gaps_exist

  user_requested_persistence:
    HIGH
```

But the system-owned loop policy still says:

```yaml
system_limits:
  max_research_rounds: 6
  max_stagnation_rounds: 2
  max_query_budget: 80
  max_runtime_budget: ...
```

Therefore:

```text
USER:
"Loop until you find 12."

SYSTEM:
tries to reach 12

BUT IF:
sources saturate
progress stops
budget ceiling reached
evidence becomes insufficient

→ EXHAUSTED / STALLED
not infinite looping
```

That is the correct balance.

> **User controls desired stopping conditions. φ retains absolute safety ceilings.**

# Separate discovery quantity from final quantity

This is especially important for Niche Loadout.

If the user says:

> “Find me 15 products.”

That could mean two very different things.

Do not change:

```text
NICHE_LOADOUT final collection = 3–6
```

Instead distinguish:

```yaml
product_preferences:

  discovery_target:
    15

  qualified_candidate_target:
    8

  final_loadout_target:
    5
```

So the run might do:

```text
discover 21
↓
retain 13
↓
validate 8
↓
portfolio optimizer
↓
final 5
```

That's much stronger than either stopping after finding five products or forcing 15 products into the final collection.

If the user genuinely wants a catalog of 20 products, Hermes can say that exceeds the `NICHE_LOADOUT` collection contract and use an expanded shortlist/report output instead.

# Every setting needs metadata

This is what makes it safe and understandable.

```yaml
setting:
  id: community_strength

  label:
    Community research strength

  description:
    >
    Controls how much independent community evidence
    the system seeks before considering community
    understanding sufficiently grounded.

  level:
    USER_SAFE

  type:
    enum

  allowed:
    - LIGHT
    - STANDARD
    - STRONG
    - VERY_STRONG

  default:
    STRONG

  mutability:
    DURING_RUN

  affects:
    - comment_query_budget
    - thread_independence_target
    - author_independence_target
    - contradiction_search_budget

  cannot_affect:
    - evidence_authority
    - prevalence_inference_rules

  cost_effect:
    STRONG_INCREASES_RUNTIME
```

That last part is useful.

Hermes can explain:

> “Very Strong comments will likely make the run longer because it increases independent thread and contradiction research.”

# Hermes should translate plain English into a `PreferencePatch`

For example:

> “I care way more about finding obscure products than speed. Go deep in Reddit/comments, don't spend too much time on suppliers, find at least 15 possibilities, then give me your best 5.”

Hermes outputs internally:

```yaml
preference_patch:

  research_depth: DEEP

  open_discovery: HIGH

  community_strength: VERY_STRONG

  assortment_style: INSIDER_HEAVY

  discovery_product_target: 15

  final_product_target: 5

  supplier_depth: LIGHT
```

Then `settings.py` validates it.

Hermes does **not** directly alter graph YAML.

# Settings revisions should be first-class SQLite state

At run start:

```text
UserPreference
↓
ResolvedSettings
↓
SQLite settings revision 1
```

Mid-run:

> “Actually go deeper on comments.”

Create:

```yaml
settings_revision:
  revision: 2

  previous: 1

  requested_by:
    USER

  patch:
    community_strength:
      STRONG -> VERY_STRONG

  effective_from:
    next_community_research_action

  retroactive:
    false
```

Never silently rewrite what earlier steps meant.

This is also useful in the final report:

```text
Run started: Balanced
Round 2: user increased Community Strength → Very Strong
```

# Allow goal-level preferences, not just parameter-level preferences

This is an important distinction.

Non-coders often don't know what parameter they want.

They know the **behavior** they want.

Examples:

> “Don't stop until you're really confident in the community.”

> “I'd rather get fewer products but weird insider ones.”

> “Explore broadly before settling.”

> “Don't waste a lot of time on Alibaba.”

> “I want at least three different sub-niches.”

> “Keep researching if the top two markets are close.”

Those should compile into multiple underlying settings.

For example:

```yaml
preference_profile:
  goal:
    "favor unusual insider products over obvious products"

resolved:
  open_discovery: HIGH
  frontier_diversity: HIGH
  outsider_obviousness_penalty: HIGH
  assortment_style: INSIDER_HEAVY
  genericness_penalty: HIGH
```

That is where Hermes adds real value over a settings page.
